# Jensen 后续优化与有界 n=6 验证

日期：2026-09-26。固定基线：`8582fbb5fcaaaa9df887173bdf9e4dcacb146217`。本轮只修改 Transfer 计数路线与相关验证工具，计数、旋转、镜像和有洞分类语义保持不变。

## 已测收益

在 AMD Ryzen 9 7940HX、Windows x86_64、Rust/Cargo 1.97.1、原有 release 配置下，每个版本预热1次，随后11轮测量，轮换各版本的执行顺序。每次启动新进程，因此图构建时间包含在算法耗时内。环境统一设置 `RAYON_NUM_THREADS=32`，Transfer 本身是串行算法。

所有 n=6 运行都由 Windows Job 限制提交内存和运行时间；阶段对照采用512 MiB、30秒，最终版另在32 MiB下成功运行3次。主程序本身没有新增全局内存限制，必须通过脚本使用该约束。

| n=6 版本 | 算法中位数 | 最小–最大 | 峰值 Job 提交内存 |
|---|---:|---:|---:|
| 已应用基线 | 4.777 ms | 4.611–5.064 ms | 11.15 MiB |
| 1：共用矩形扫描 | 4.337 ms | 4.291–4.503 ms | 11.23 MiB |
| 2：终止累计＋缓冲复用 | 4.072 ms | 3.963–4.153 ms | 11.29 MiB |
| 3：29位整数状态键 | 3.692 ms | 3.622–3.861 ms | 7.28 MiB |
| 4：拓扑图＋计数数组 | 2.678 ms | 2.629–2.753 ms | 16.77 MiB |
| 5：有洞吸收桶，最终版 | **2.217 ms** | **2.166–2.510 ms** | **12.53 MiB** |

n=6算法约快2.15倍，时间减少约53.6%。最终版内存低于第4步，但略高于基线；本轮的优化目标偏重计算速度，并以硬内存上限约束资源。第3步是内存更小但计数较慢的已归档候选，没有给生产程序增加额外算法选项。

n=5 同轮对照：0.568→0.232 ms，约快2.45倍。n=6三分类仍为：总数410,964,612、无洞112,877,832、有洞298,086,780。

**不能把内核收益当作完整进程收益。** 本轮启动器从 CreateProcess 前计时至子进程退出，基线和最终版n=6进程中位数分别27.361、27.442 ms；n=5分别22.185、22.037 ms，没有测出明确的端到端改善。进程时间包含Windows创建、装载、调度、输出等成本，不包含PowerShell编译辅助类、解析日志和写JSON。该口径与上一轮普通命令启动测量不同，不横向拼接两轮CLI数据。

峰值指标来自Job Object的 `PeakJobMemoryUsed` / `PeakProcessMemoryUsed`，反映提交内存，不是RSS工作集或系统全部内存。32 MiB验证用于证明资源约束下可完成，不与另一批次的计时作性能归因。

## 实现与正确性依据

1. **矩形复用。** 同宽C(w,w)与C(w,w+1)共享前w行。行末只读取累计值，继续保留可生长前沿。所有尺寸到5的格扫描阶段由95降至65，到6由161降至106；这不是耗时比例。
2. **闭合累计。** 唯一四连通组件消失后，后缀只能全空，其贡献只记入终止累计器一次；行快照加上当前活跃连通形状。只剩一个前沿组件不代表已经结束，不能提前移入累计器。
3. **紧凑编码。** 六个标签各3位，加角占用、phase和χ共29位。中间版本用它作为完整状态键；最终版用于不含χ值的拓扑图建表。生产计数不再逐格哈希完整历史。
4. **转移图。** 节点身份包括规范化连通标签、old_left、phase、扫描列。每宽度建立可达拓扑图，边保存下一个编号及Δχ；计数数组按节点和χ桶索引，活跃列表避免扫描空桶，两组数组交换复用。
5. **有洞吸收。** 逐行扫描的未处理后缀始终四连通到板外。因此已封闭空洞不含未处理格，后续不能填掉。非空前缀χ≤0足以确认有洞，归入永久桶0；初始空前缀phase=0、χ=0保持独立，首次占格进入χ=1。正χ仍精确保留，不能提前判无洞。

χ满足闭方格复形关系χ=c8−h，c8是允许角接触的前景分量数。每个活跃四连通组件仍须在前沿，故正χ≤c8≤c4≤前沿宽度；最终只需0..MAX_N共7个桶。old_left仍参与左上角顶点去重，不能随χ压缩删除。任意顺序的形状生长可能以后填洞，这里的吸收规则只针对固定逐行扫描。

旋转固定点、Gray code枚举、Burnside以及导出路线没有改写。也没有采用45°包围盒或额外面积维度剪枝。

## 验证覆盖

- `cargo test --release --locked --offline`：26项主程序、7项probe、5项CLI，共38项通过。
- `cargo test --locked --offline`：同样38项通过。
- 独立坐标与前景/背景洪泛oracle仍覆盖n≤4；新测试逐项比较所有宽高≤5的行快照与冻结参考实现。
- n≤5继续与BFS、Canonical计数及既有导出集合测试交叉验证。
- n=6基线、每阶段候选、最终Release及Debug版本均经有界启动器验证三分类结果。Debug运行检查数组与χ边界断言。
- n=6没有独立穷举全部形状；证据是与冻结基线和历史结果一致，并结合小规模独立oracle。此次没有重新生成n=6数据集。
- Windows启动器专项验证：64MiB限额下独立程序申请256MiB被拒；睡眠程序超时终止；非零退出、伪造错分类、缺失行及非空输出目录均按预期失败。

Windows可能不交付所有内存限额通知，工具不会把“没收到通知”当作“失败必然与内存无关”；未观察到通知的失败原因记录为unknown，仍使测量失败。

## 可复现的有界入口

在 `rust` 目录执行：

```powershell
cargo build --release --locked --offline
# 默认n=5，不会隐式运行n=6
./scripts/measure-transfer.ps1 -Exe ./target/release/room-count.exe
# 本轮用户已明确授权的n=6，32MiB，30秒超时
./scripts/measure-transfer.ps1 -Exe ./target/release/room-count.exe -N 6 -MemoryMiB 32 -TimeoutSeconds 30 -Runs 9
```

每次运行使用新输出目录，保存二进制SHA256、实际argv、全部计数、算法时间、进程时间、峰值内存、退出码及完整日志。子进程以挂起状态创建，挂入已配置限制的Job后才恢复执行；任一步失败都不会降级成不限内存运行。关闭Job会终止尚存的子进程。Windows 64位PowerShell是此测量工具的要求，Rust算法不依赖Windows API。

阶段对照脚本、每阶段二进制、轮换基准原始数据、完整测试日志和独立终审随本轮交付材料保存。固定的第一批参考实现仅在测试配置下编译，防止优化实现与预期同时改变。
